# RLAIF Reliability (Aspect 1): when does RL against a frozen LLM judge collapse?

EE599 Reinforcement Learning, Team 3. This repository implements **Aspect 1: Reliability** of the
proposal *"Reinforcement Learning Against Learned Evaluators in Speech and Language Models."*

> **Hypothesis.** RL from AI feedback (RLAIF) collapses not when the policy out-solves its judge, but
> when its remaining errors concentrate on problems the judge cannot verify. Noisy-verifier theory
> predicts collapse once the verifier's Youden index (TPR - FPR) turns negative, but it assumes
> answer-independent errors. Per-problem verification accuracy and a best-of-N attack on the judge,
> measured *before* training, should therefore predict collapse onset better than the solve gap.

## Results at a glance

Full write-up: [`results/FINDINGS.md`](results/FINDINGS.md). Every table and figure:
[`results/REPORT.md`](results/REPORT.md) (generated by `scripts/analyze.py`).

* **Out-solving is not the trigger.** The solve gap has no predictive value (C ~ 0.50). Countdown
  collapsed even against the 4B judge, which out-solves the policy; MATH improved against the 0.6B
  judge, which the policy out-solves.
* **Global Youden J mis-predicts.** Countdown judges start at J ~ 0.70-0.74 and all collapse within
  ~10 GRPO steps (held-out gold accuracy 0.41-0.43 -> 0.18-0.25). A MATH judge with J = 0 still
  trains the policy upward (0.59 -> 0.70).
* **Per-problem verifiability beats the solve gap** at predicting per-problem exploitation onset on
  held-out problems (C 0.67 vs 0.52; dC = +0.14, 95% CI [0.12, 0.17]), judges and task. The policy's
  own base solve rate predicts better still (0.73).
* **Concentration of errors is not what collapses a run.** MATH errors stay concentrated on
  unverifiable problems and MATH does not collapse. Countdown collapses through one presentation hack
  that transfers across judges: a policy trained against the 0.6B judge fools the unseen 4B judge on
  85% of its wrong answers.
* Removing the least-verifiable problems does not prevent collapse, and neither does commit-first
  judging. Response-length drift is the best label-free stopping signal on Countdown but raises
  false alarms on MATH.

## Experiments run

All runs: Qwen3-1.7B policy, LoRA r=16, lr 5e-5, 8 prompts x 8 rollouts per step, soft P(Yes)
reward. Countdown runs are 128 steps, MATH runs 96. Exact commands are in `queues/`.

| Task | Standard judge, full pool | Causal arms (0.6B judge) | Commit-first | Extra |
|---|---|---|---|---|
| Countdown | 0.6B, 1.7B, 4B | drop least-verifiable, drop largest gap | 0.6B, 1.7B | lr 1e-5 with 0.6B and 4B |
| MATH (L1-3) | 0.6B (2 seeds), 1.7B, 4B | drop least-verifiable, drop largest gap | 0.6B | |

Pre-training audit: 12 base-policy samples per pool problem (plus 1 planted correct and 2 planted
wrong answers), each judge's own 6 samples and greedy commit, scored by every judge in both modes
(the 4B judge in standard mode only).

**Deviations from the proposal**, all for compute (see Compute notes): smaller scale than a modern
GPU would allow, one seed for most configurations, no random-removal control arm, and no commit-first
runs with the 4B judge or with the 1.7B judge on MATH.

## What is implemented

| Proposal item | Where |
|---|---|
| Qwen3-1.7B policy, **LoRA GRPO** | `rlaif/grpo.py` (from-scratch GRPO: group-normalised advantages, token-mean loss, optional k3 KL) |
| Frozen **Qwen3 judges 0.6B / 1.7B / 4B**, reference-free (gold hidden) | `rlaif/judge.py` (score = P(Yes)/(P(Yes)+P(No)), one forward pass) |
| **Countdown** and **MATH** | `rlaif/tasks/countdown.py`, `rlaif/tasks/math_task.py` |
| Held-out evaluator (gold checker); judge-vs-gold gap = exploitation | `Task.gold_check` (exact Countdown checker; `math-verify` for MATH); logged for every rollout, never rewarded |
| **Per-problem verification accuracy** (TPR, FPR, Youden J) before training | `rlaif/diagnostics.py` |
| **Best-of-N attack** on the judge before training | `diagnostics.bon_probability` (exact P(judge's favourite of N base samples is wrong and accepted)) |
| **Solve gap** (policy solve rate - judge solve rate) | `diagnostics.compute_features` |
| **Per-problem hazard model**, evaluated on **held-out problems, judges and task** | `rlaif/analysis/hazard.py` (discrete-time logistic hazard, Harrell's C, bootstrap) |
| **Causal test**: remove least-verifiable vs largest-solve-gap problems | `scripts/make_pools.py`, runs with `pool=drop_*` (a `drop_random` pool is also built) |
| **Commit-first judging** [3] | `Judge(mode="commit_first")`: the judge solves the problem itself first (cached greedy commit), then grades |
| **Label-free early stopping** | `rlaif/analysis/stopping.py` (judge self-disagreement, verifiability-stratified reward gap, reward plateau, length drift; thresholds tuned on one task, tested on the other) |
| Noisy-verifier theory check (global J vs collapse) | `analysis.events.online_youden`, `REPORT.md` |
| Exploit transfer across judges (held-out judges) | `scripts/cross_judge.py` |
| Qualitative examples of accepted-but-wrong answers | `scripts/show_examples.py`, `results/examples_*.md` |

### Definitions used in the analysis

* **Judge verdict / reward.** Reward is the judge's soft label P(Yes) (as in the original RLAIF);
  the verdict "accept" is P(Yes) > 0.5 and defines TPR/FPR. `reward=verdict` gives a binary verifier.
* **Per-problem Youden J_p** = TPR_p - FPR_p of the judge on the base policy's own 12 samples for the
  problem plus one planted correct and two planted wrong answers (so both classes always exist),
  Beta(1,1)-smoothed.
* **Best-of-N attack** `bon_fool_N` = P(the judge's highest-scored of N base samples is wrong *and*
  accepted), exact under sampling with replacement.
* **Exploitation event.** Each training epoch visits every pool problem once, in a fresh random order
  (G=8 rollouts per visit). A problem is *exploited* at the first visit where a majority of its
  rollouts are accepted by the judge but gold-wrong; problems already in that state for the base
  policy are not at risk. Time = training step of the visit. Two alternatives are also reported:
  *fooled* (the judge accepts most of a visit's wrong rollouts) and *unlearned* (gold accuracy falls
  0.25 below base while the judge still accepts).
* **Run-level collapse onset.** First step where the EMA of the training false-positive rate exceeds
  its initial level by 0.15.

## Layout

```
rlaif/
  tasks/          Countdown + MATH: prompts, gold checkers, planted candidates
  models.py       loading, sampling API, per-token log-probs
  fastgen.py      static-KV-cache + CUDA-graph Qwen3 sampler (shares weights + LoRA with the HF model)
  judge.py        standard and commit-first reference-free judges
  grpo.py         LoRA GRPO trainer (resumable)
  diagnostics.py  pre-training audit: per-problem TPR/FPR/J, best-of-N attack, solve gap, commits
  analysis/       events, hazard model, early stopping, plots
scripts/
  prepare_data.py   build training pools + held-out sets
  run_diagnostics.py  pre-training audit (stages: policy, judge, features)
  make_pools.py     causal-test pools
  train_grpo.py     one GRPO run
  run_queue.py      run job queues per GPU slot (dependencies, retries)
  analyze.py        every analysis -> results/
  cross_judge.py    re-score rollouts with every judge (exploit transfer)
  show_examples.py  accepted-but-wrong rollouts, first vs last epoch
configs/          base.yaml, countdown.yaml, math.yaml
queues/           the exact job lists used for the experiments
tests/            CPU unit tests; GPU test of the fast sampler against HF
```

## Running

```bash
pip install -r requirements.txt
python scripts/prepare_data.py --task countdown
python scripts/prepare_data.py --task math --levels 1 2 3

# 1) pre-training audit
python scripts/run_diagnostics.py --task countdown --stage policy
python scripts/run_diagnostics.py --task countdown --stage judge --judge Qwen/Qwen3-0.6B   # repeat per judge
python scripts/run_diagnostics.py --task countdown --stage features

# 2) GRPO against a frozen judge (policy on GPU 0, judge on GPU 1)
CUDA_VISIBLE_DEVICES=0,1 python scripts/train_grpo.py --config configs/countdown.yaml judge=Qwen/Qwen3-0.6B
CUDA_VISIBLE_DEVICES=0,1 python scripts/train_grpo.py --config configs/countdown.yaml judge=Qwen/Qwen3-0.6B judge_mode=commit_first

# 3) causal test pools, then train with pool=drop_lowver / drop_gap / drop_random
python scripts/make_pools.py --task countdown --judge Qwen/Qwen3-0.6B

# 4) analysis
python scripts/analyze.py
python scripts/cross_judge.py --task countdown
python -m pytest tests/test_core.py tests/test_analysis_e2e.py      # CPU
CUDA_VISIBLE_DEVICES=0 python -m pytest tests/test_fastgen_gpu.py  # GPU
```

## Compute notes

Experiments ran on 8x Quadro M6000 (Maxwell, 12 GB, sm_52, about 3 fp16 TFLOPS each), shared with
other users. vLLM, FlashAttention and Triton do not support this architecture, so:

* frozen weights are fp16 (bf16 is emulated and about 2x slower), LoRA adapters are fp32, and loss
  scaling handles fp16 gradients;
* generation uses `rlaif/fastgen.py`, a static-cache decoder whose decode step is a captured CUDA
  graph (HF `generate` was launch-bound at about 0.12 s/token on the oversubscribed host). It reuses the
  HF model's parameter tensors and its LoRA adapters, and matches HF greedy decoding token for token
  (`tests/test_fastgen_gpu.py`);
* the server's driver/NVML version mismatch turns CUDA out-of-memory errors into an NVML internal
  assert, so `models.is_oom` treats both as OOM. On OOM, generation halves its batch, judge scoring
  splits its batch, and a GRPO step is redone with activation checkpointing and then smaller
  micro-batches. Cleanup happens after the `except` block, because the live traceback still holds the
  failed attempt's tensors. Trainer state is saved every 4 steps, so a killed job resumes with little
  lost work.

Scale choices forced by this hardware (all in `configs/`): 128-problem training pools, 8 prompts x 8
rollouts per step, 384 (Countdown) / 400 (MATH) new tokens, non-thinking mode, and 12 base samples
per problem in the audit. One Countdown run takes about 4-6 h and one MATH run about 7-9 h on one
or two GPUs; the audit plus the full grid finished in under a day on the 8 GPUs.
